## 2. Domínio & Dados

**Cliente:** Mr Lion (mel, capuccino, blended, acessórios)

**Schema Supabase (`supabase/schema.sql`):**
- `products` — 4 categorias (honey, cappuccino, blended, acessorio) + `current_stock` + `min_stock`
- `locations` — 4 tipos (deposito, loja_fisica, marketplace, ecommerce) — 6 locais seed (Depósito Central, Angelo/Degusto, Porquinho, Rio Comprido, Mercado Livre, NuvemShop)
- `location_stock` — source of truth por local
- `stock_movements` — append-only (in/out/adjustment/loss/transfer)
- `delivery_orders` — status (pending/confirmed/delivered/cancelled) com items JSONB
- `profiles` — role (operator/manager) + location_id
- `alerts` — threshold por produto
- RLS por role e location_id (sólido)
- Functions: `update_stock`, `transfer_stock` (atômica com FOR UPDATE)

**Diagnóstico schema:** ✅ Bem desenhado. Transferência atômica, append-only movements, RLS multi-tenant por location. Sólido.

## 4. Gaps Funcionais (vs. referências TOTVS / vhsys)

O usuário forneceu 2 referências (TOTVS WMS + vhsys ERP). **NÃO seguir tudo** — filtrar pelo que faz sentido para operação Mr Lion (mel artesanal, 6 pontos de venda, B2B + B2C marketplace).

### ✅ Já implementado
- Multi-localização (produto por loja) — **diferencial forte**
- Movimentações append-only (auditável)
- Transferência atômica entre locais
- Alertas de estoque mínimo
- Realtime via Supabase
- Roles + RLS
- Dashboard por loja

### 🎯 Gaps de alto valor para Mr Lion
1. **Lotes + validade** — crítico (mel tem validade; capuccino idem). Tabela `product_batches` com `batch_code`, `expiry_date`, `quantity`. Alertas "N dias para vencer".
2. **Código de barras / SKU scanner** — entrada rápida via webcam ou dispositivo. Atualiza estoque em 2 cliques.
3. **Estoque mínimo E máximo** — hoje só mínimo. Máximo evita excesso (capital parado).
4. **Reposição sugerida** — baseada em giro (últimos 30/90 dias) + mínimo. "Comprar X unidades de Y".
5. **Curva ABC automática** — por receita ou por giro. Prioriza atenção nos que faturam.
6. **Análise de perdas / acurácia** — relatório dedicado. Quanto se perdeu por local/categoria/período. Hoje existe `action='loss'` mas não há tela agregada.
7. **Inventário cíclico** — contagem periódica com diff (físico vs. sistema). Crítico para auditoria.
8. **Fornecedores** — cadastro + último preço + histórico. Impacta custo.
9. **Preço de custo + margem** — colunas hoje ausentes em `products`. Sem isso não dá para calcular lucratividade.
10. **Notificações multi-canal** — push/email quando vencimento/ruptura. Hoje só toast dentro da app.

### ⚠️ Features TOTVS/vhsys que NÃO fazem sentido (descartar)
- Emissão de NF-e/NFC-e (tem provedor especializado; não é core)
- YMS / gestão de pátio (Mr Lion não tem frota)
- Kits complexos com BOM (não há produção no sistema)
- Integrações ERP externo (ainda não é a escala)
- Marketplace sync automático (fase futura)

## 5. Problemas de UX (inferidos da arquitetura)

Hipóteses com base em arquivos monolíticos, precisam validação com screenshot/uso:

1. **Navegação:** 8 rotas no menu — muito para operador. Consolidar em ~4 seções (Estoque / Pedidos / Catálogo / Relatórios).
2. **StockEntryPage (1.875 linhas):** provavelmente mistura várias ações (entrada, saída, ajuste, perda, transferência). Cada ação merece fluxo dedicado e curto.
3. **OrdersPage (1.985 linhas):** lista + detalhe + confirmação + cancelamento + entrega tudo em uma tela. Separar em drill-down.
4. **Dashboard (650 linhas):** muita informação competindo. Aplicar hierarquia visual (KPIs grandes no topo, detalhe abaixo).
5. **Componentização shadcn:** alguns primitivos já customizados (badge/button/tabs); padronizar tokens no design system.
6. **Mobile:** PWA está ligado mas layout precisa validação em mobile real (operador em loja mexe pelo celular).

| Adotar **Storybook** ou cenário similar para componentes core | Velocidade de UI work |
| Consolidar hooks duplicados (useStockMovements 382 linhas) | Menos bugs |
